# TVCast 屏幕镜像（二期-2）设计 Spec — 已确认

> 日期：2026-10-23 ｜ 状态：**已确认（2026-10-23 用户拍板，按推荐项执行）** ｜ M-A 传输原型已完成（`:transport` 模块）；**M-B 手机端采集编码已完成**（`:sender` mirror 包，模拟器 E2E：授权→采集→硬编→UDP→重组→NACK→码率档位全链路 20-29fps）
> 前置：v2.0.0 双 App 已发布；`:dlna` 共享模块与双端架构就绪

## 1. 目标与范围

手机屏幕实时镜像到电视：MediaProjection 采集 → 硬件编码 → 局域网传输 → TV 端低延迟解码渲染。

**目标延迟**：同局域网 ≤ 200ms（采集到上屏）。这是与 DLNA 推流（秒级启动）的本质区别。
**明确不做**：跨网段/公网镜像、iOS/桌面端、音频采集（二期 V2.1 再加，AudioPlaybackCapture API 29+ 限制多）。

## 2. 架构

```
手机端（sender 扩展）                    TV 端（app 扩展）
┌─────────────────────┐               ┌─────────────────────┐
│ MediaProjection      │               │ 码流接收与重组        │
│  └→ ImageReader      │  传输层       │  └→ MediaCodec H.264 │
│     (RGBA_8888)      │ ──────────→  │     硬解（低延迟模式） │
│  └→ MediaCodec 硬编  │  自研 UDP 或  │  └→ Surface 渲染     │
│     H.264 (CBR+LTR)  │  libwebrtc   │      (PlayerView)    │
│  └→ 控制信道（TCP）   │ ←──────────  │  └→ NACK/统计回传    │
└─────────────────────┘               └─────────────────────┘
```

- 竖屏投横屏电视：镜像内容按比例缩放信箱（letterbox），不旋转采集
- 码率自适应：目标 4~8 Mbps（1080p），按丢包/RTT 降档（2/4/8 Mbps 三档起步）

## 3. 传输层方案（需定稿二选一）

| 维度 | A. 自研 UDP 分片 + NACK/FEC | B. libwebrtc |
| --- | --- | --- |
| 延迟潜力 | 相当（少一层封装） | 相当 |
| 实现量 | ~1.5k 行（分片/序号/NACK/简单 FEC/拥塞档位） | 集成为主，但双端引 ~30MB .so、API 复杂 |
| 可控性 | 完全可控，协议在自己手里 | 黑盒调优难 |
| 弱网抗性 | 起步版靠 NACK + 码率降档；FEC 二期补 | 成熟（jitter buffer/pli/fec 全套） |
| 风险 | 弱网调参是深坑 | 集成与裁剪坑、包体大 |

**建议**：方案 A。理由：局域网场景（RTT<5ms、丢包<1%）下 NACK+降档足够达标；协议可控与体积小对项目长期价值更高。libwebrtc 留作 M-A 不达标时的回退选项。

**M-A 验收门槛**（原型期命令行双端对测，无 UI）：1080p 码流，模拟器/两台真机，丢帧率<0.5%、端到端 P95 延迟<250ms；不达标则回方案层重评估。

## 4. 里程碑

| 里程碑 | 内容 | 验收 |
| --- | --- | --- |
| M-A 传输原型 | UDP 分片/重组 + NACK + 码率档位；JVM 双端对测工具（复用 :dlna 模块模式，纯 Kotlin） | 上述门槛 ✅ |
| M-B 手机端采集编码 | MediaProjection 授权流、ImageReader→MediaCodec（Surface 输入直通）、旋转/分辨率处理 | 真机采集编码稳定 30fps（模拟器 E2E 已过，真机待验）✅ |
| M-C TV 端渲染 | 码流接收→MediaCodec 低延迟解码→Surface；镜像 UI（待机页新增"屏幕镜像"入口，复用发现机制） | 真机投屏延迟实测 |
| M-D 打磨 | 码率自适应调参、断连重连、音频（可选）、错误 UI | 真机清单（见 §5） |

## 5. 真机测试清单（预告）

手机（Android 10+，MediaProjection 需动态授权）→ 雷鸟电视：静态桌面/视频 App/游戏三类场景各测延迟与卡顿；锁屏来电中断恢复；WiFi 2.4G/5G 对比。

## 6. 风险

| 风险 | 对策 |
| --- | --- |
| 弱网调参深坑 | M-A 门槛制；不达标回退 libwebrtc |
| 各 ROM MediaProjection 限制 | 首帧前引导授权；失败明确报错 |
| 老电视硬解延迟高（低延迟模式 API 不足） | 尽量用 `MediaCodec` 低延迟 key；不行则退级到普通模式（延迟↑但可用） |
| 音频缺失体验 | 二期 V2.1 规划，spec 阶段明示 |

## 7. 决策点（2026-10-23 已确认）

1. 传输层走方案 A（自研 UDP）✅ — M-A 已按此实现并通过有损回环测试
2. 首版分辨率/码率档位：1080p / 4-8Mbps 起步 ✅
3. 音频推迟到 V2.1 ✅
